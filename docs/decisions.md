| 2026-10-08 | Stable runtime is a pinned independent checkout | Branch switches and unfinished edits cannot affect daily service. |
| 2026-10-08 | Private database/deployment/account config stay outside Git | Prepare repository for possible public release. |
| 2026-10-08 | Chat approves immutable Q versions | Web-triggered execution remains unverified. |
| 2026-10-08 | Deterministic deadline/status logic precedes Luna summaries | Raw-input trial made boundary/uncertainty errors; revisit using scored/live evidence. |
| 2026-10-08 | Actual browser startup/routes are acceptance checks | Node imports concealed global scope collision. |
| 2026-10-08 | Phase5 remote executor is NO-GO; retain exact Q-version chat approval | [Feasibility assessment](outlook-feasibility.md): provider support does not establish authorized account access, unattended reliability or trusted approval ingress. | 2026-10-09 | Trial coordinator/CLI-worker workflow with fixed model routing and SHA-bound review | [Agent workflow](agent-workflow.md): separate planning, writing and review contexts may reduce rework, but efficiency is unproven. Adopt only by user decision after #21 pilots versus a single-agent baseline; revisit routing on observed usage. |
| 2026-10-09 | Codex quota below 10% in any applicable window hands approved pending work to a Claude Code fallback coordinator | [Quota handoff](agent-workflow.md#quota-handoff): keeps authorized work moving without new authority; unknown readings never count as zero. Policy only, not a monitor; revisit after an observed real handoff or a change in quota reporting. |
| 2026-10-09 | Claude Opus 5.5 high is the default for all ordinary planning, design, implementation, tests and review; Astra only for audited exceptional tasks with a recorded reason; written per-request publisher delegation (push/PR only) | User routing change. Keeps the root coordinator on intake, review and summary, and gives one execution lead bounded authority without making workers publishers. No merge, release or deploy. Revisit with #21 usage and quality evidence. |
| 2026-10-09 | Every request updates a private RESULT record; previous versions are archived immutably; repairs are derived copies | A captured result was silently mis-encoded, and overwritten records leave no history. RESULT stays authoritative; any status page is derived and makes no live claims. |
| 2026-10-11 | Claude CLI contexts run `-p --no-session-persistence` with private per-request/attempt evidence; one Herdr workspace and RESULT per request | [Quiet CLI sessions](agent-workflow.md#quiet-cli-sessions): persisted `-p` runs appeared as many app sidebar tasks. Gives up native resume; recovery uses checkpoints and Git. Revisit if the [smoke test](worker-session-test.md) still shows such runs, or the flag changes. |
| 2026-10-09 | Effort calibration counts only explicitly confirmed, server-frozen positive estimate/actual pairs; median, three-sample minimum, zero excluded; any actual edit invalidates | [Sample contract](data-contract.md#effort-calibration-samples-phase-6a-26): conservative, descriptive and reversible; a dedicated endpoint prevents forged pairs and read-time checks cover older code. Revisit threshold, weighting or automatic estimate use only with observed samples and a user decision. |
| 2026-10-09 | Workload modes are two explicit advisory Home views (Standard default, Reduced = urgent required first); verification and coverage warnings are never hidden | [Mode contract](data-contract.md#workload-modes-phase-6b-27): changing emphasis is reversible and cannot hide uncertainty or imply capacity; a dedicated validated endpoint keeps invalid modes out. Revisit more modes, capacity estimates or scheduling only with observed use and a user decision. |
| 2026-10-09 | Career Roles/People order uses only each item's explicit saved (first) or dismissed (last) status; other statuses keep source order; dismissed items stay visible with Restore | [Ordering contract](data-contract.md#career-feedback-ordering-phase-6c-28): transparent and reversible, cannot hide eligibility unknowns or learn unconfirmed preferences. Eligibility that missing profile facts cannot support is labelled "not assessed" on the page rather than changing the eligibility check. Revisit scores, cross-item learning or more feedback signals only with observed use and a user decision. |
| 2026-10-09 | Weekly trends compare two dated weeks (Monday–Sunday, snapshot timezone, by `generatedAt`) using only bounded observed counts and source health; non-ok or unreported sources, unread retained evidence, retention-limited weeks and truncated reads are "Not comparable" with no change shown | [Trends contract](data-contract.md#weekly-evidence-trends-phase-6d-29): collection time is when evidence was true, while import time can lag. Treating any coverage gap as non-comparable means a failed source can never read as an improvement, and "No observations" is never zero. Revisit metrics, comparability rules or longer retention only with observed use and a user decision. |
| 2026-10-11 | After every parent merge in a PR stack, reconcile dependent branches one at a time with non-rewriting merges. Keep the child's side of a conflict only after auditing that the base is a verified squash of a parent head the child contains. Accept the result only when every full-tree difference from the approved child maps to a base commit and the own range holds only unmerged work | [Post-merge reconciliation](development-workflow.md#after-a-parent-pr-merges): squash merges give identical content a new identity, so a stale stack conflicts and lists duplicate history even when the base brought nothing new. A blob match elsewhere in history could silently drop a base revert or fix, so intended base changes are resolved by hand and mapped. The lifecycle step existed but was not run after each merge. Revisit if the merge strategy or stacking changes. |
| 2026-10-12 | Personal Gmail (read-only snapshot: inbox, 7 days, ≤50, metadata/snippets) and Google Calendar replace Outlook as active providers, collected by existing assistant connectors with no OAuth/token store; only the active calendar source invalidates coverage; provider identity joins new fingerprints | User request DW-GOOGLE-01: the school Outlook connector session was never established (#14, restriction unresolved), while personal Google connector identity and primary-calendar owner access were verified. Snapshot-only access keeps the app free of credentials and honest about freshness; strict completeness rules stop a single page or a failure from reading as an empty inbox or free time. Revisit scope (window, attachments, sending) only by explicit user request. |
| 2026-10-12 | Daily plans are generated only on explicit request by a deterministic planner that needs fresh complete Google coverage of 09:00–24:00, uses only explicit durations and deadlines, keeps 20% free, and outputs ordinary proposals; email reaches todos only through explicit adoption | User request DW-GOOGLE-01 task 2. A deterministic, explained plan is reviewable and reproducible; refusing to plan on incomplete coverage keeps unknown time from reading as free; reusing proposals keeps the Q-version approval path unchanged. Revisit block length, reserve, ordering or automatic triggers only with observed use and a user decision. |
| 2026-10-12 | Google Calendar writes are performed only by the root assistant after explicit chat approval of an exact Q version, through a local verify → live recheck → pending → single write → field-by-field read-back → reconcile procedure; initial scope is one-time personal creates on an owner calendar with no attendees | User request DW-GOOGLE-01 task 3. Keeps credentials and network out of the app, binds approval to store, version, fields and source tasks, and blocks rather than drops unsupported fields; unknown outcomes are never retried blindly. Phase 5 autonomous executor stays NO-GO. Revisit updates, recurrence or automation only after observed approved writes and a user decision. |
| 2026-10-12 | A started action's protection is the copy matching its receipt fingerprint, never a stale same-ID copy; own started events (receipt `remoteRef`, or exact approved copy) count as allocations, not lost capacity | Review round 2 of DW-GOOGLE-01 task 2: stale restored copies let overlapping requests through, and imported own events eroded the 20% reserve. Unknown time fails closed instead of being guessed. Revisit if the collector supplies an authoritative Dayweave marker per event or a retention limit for started blocks is added. |
| 2026-10-12 | Every marked event a started claim sees is kept across its outcomes (identity = calendar + event ID); two or more distinct ones, seen by one search or across several (any calendar, complete or not), hold an action; the hold records the windows, calendars and matches seen and clears only with a complete single match covering all of it (≥24 hours either side); with one seen, only that event is read back and `not_created` is refused; an unknown range (no or unreadable scope, invalid search bounds, a marker with unreadable times or no ID, an outcome recorded before marked events were kept) stays unknown and needs the human; every `not_created` version reference stays in receipt history and refuses new claims under that version, while already started claims record their outcome; snapshot imports cannot add Google-shaped receipts, and under Google coverage only receipts for locally stored Outlook proposals, never replacing local ones | Issue #46 and its two reviews: a narrower search or a direct read-back could hide a second event (also one seen by an incomplete read, on another calendar, by an earlier outcome that saw only one, or by an older search whose range was never recorded), a later attempt overwrote the version that had failed so an old approval could reopen it, and imports could insert receipts with no local pending journal, including through a proposal in the same import. Failing closed may need a wider read, a new approved version or a human decision, never a guessed range. Receipts move only with the database; backups are trusted local data. Guards are consistency checks, not authentication. Revisit if the connector supplies a provider idempotency key or authoritative event provenance, or when a human-resolution command for unknown holds is requested. |
| 2026-10-13 | The supervising launcher proves ownership with a lock-secret challenge over a local channel, creates the lock before anything else and reserves the port before the Store opens, treats any unverifiable holder, possibly live child or foreign listener as unknown (exit, no stealing, no termination), and restarts only its own app process within a bounded budget that stops on any config, revision or port change | DW-1006 reproduced the six DW-1002 legacy-launcher limitations in real subprocesses: pre-config errors lost, any HTTP 200 accepted as the service, exit 7 on an unwritable log, two Store opens in a start race, and no recovery. PIDs are reused and any process can answer 200, so neither is identity; stealing an unproven lock or killing an unknown process could hit an unrelated program, so availability yields to safety and unknown states need a human. Same-user code with access to the state directory is trusted. Revisit after observed sign-in, sign-out and recovery on the real machine, or if same-user code must be distrusted. |
| 2026-10-21 | A separate `web/` front end (React, Vite, TypeScript, Tailwind) serves a public demo with fictional data and can also talk to the local server; the server keeps zero runtime dependencies | User request DW-1010/DW-1011 (Milestone 2): a deployable, bilingual (EN/中文) portfolio demo on GitHub Pages. The planning rules stay in `src/*.cjs` and the web build evaluates those same files, so there is one rule set. The demo keeps visitor changes in browser storage and simulates approved writes; it never connects an account. Revisit when the private instance (#55) needs server-rendered pages or the old `src/web` UI is retired. |
| 2026-10-22 | The private instance (#55) signs in one allowlisted Google account by OIDC code flow with stateless signed cookies; ingest uses a separate bearer secret; one Fly.io machine with SQLite on an encrypted volume | Owner chose Google sign-in over passkeys (less code, smaller surface, existing Google account). Stateless sessions survive auto-stop. Revisit if more than one machine or account is needed. [Procedure](private-instance.md) |
| 2026-10-22 | Email collection reads only the Gmail label `Yale`, filled by auto-forwarding from the school mailbox, instead of the personal inbox | The owner wants school mail, not personal mail; the Microsoft connector needs school admin consent, which is not bypassed. Revisit if the school disables forwarding or approves a read-only connector. |
| 2026-10-23 | Cloud collection (#56): a Claude cloud scheduled task reads Google Calendar and Gmail by connector, the server reads the Canvas ICS feed (URL kept in host secrets), and a tested script builds the snapshot from the current one; Canvas only updates due times and adds unknown/uncertain records | The private instance must refresh without the owner's computer; the feed gives no submission or requirement state, so curated fields are carried forward and nothing is inferred | [Cloud collection](cloud-collection.md); revisit if Canvas allows personal API tokens for submission state |
| 2026-10-24 | The offline AI scripts (`ai:generate`, `eval:ai`) default to Claude Haiku 5.5 at low effort with a US$0.25 cap per script run; Opus or Sonnet only by `DAYWEAVE_AI_MODEL` | Cost is a primary project metric. The site and the daily collection call no API (the collection runs in a Claude cloud session on the subscription) | Raise the model only if a Haiku eval run fails cases that Opus passed |
| 2026-10-27 | Approved Google Calendar writes for the private instance: the owner approves an exact Q version on the signed-in page, and a separate Claude cloud task with the Google Calendar connector and its own secret runs the existing bridge steps through `/api/execute` (create only) | The owner wants approved plans written to Google Calendar without a chat round-trip. Supersedes the chat-only approval for the hosted instance; the Outlook NO-GO (#14) is unchanged. Revisit if the connector gains client event IDs, or for moving or deleting written blocks |
| 2026-10-27 | The planner adds the owner's planning rules (planning hours, meal breaks, weekly goals for gym, job applications and LinkedIn), review time before quizzes and exams, and preparation time for interview mail ahead of everything else; the recommended rules apply until the owner saves their own, and the sleep window floor moves from 09:00 to 07:00 | The owner wants a full daily plan, not only coursework blocks, and asked for exam review and interview preparation explicitly.
