# Outlook authorization and trigger feasibility

Decision date: 2026-10-08. Scope: issue #14, documentation and permitted read-only checks. Assessment baseline: fetched `origin/main` at `3197961d096c487049948728723f812c673aa40e`, including startup fix #10 and governance #12. Reconciled with main `debcce9` on 2026-10-09, preserving the merged #13 governance and operational-acceptance guidance. This assessment does not accept issue #1 or establish routine reliability.

## Decision

**NO-GO for implementing or enabling a remote Outlook executor now.** Supported provider mechanisms exist, but the permitted identity probe did not establish an authorized connector session. Calendar access, tenant consent, write permission, login renewal and unattended delivery remain unverified. No supported end-to-end Dayweave approval-to-executor channel has been demonstrated.

**GO for retaining local review and the existing human chat-approval workflow**, conditional on independently verifying authorized source access on each run. It does not authorize a calendar write. Scheduled refreshes remain read-only. Email remains disabled. No OAuth registration, consent change, token acquisition, subscription, automation creation/change, provider mutation, messaging, submission, release or deployment was performed.

| Authorized Outlook browser session | Human-supervised account/calendar/timezone verification under existing Phase 2 procedure. | Retained conditional fallback; not tested here and not a reliable unattended executor. Use only where organization policy permits that session and operation. |

Microsoft documents [delegated access](https://learn.microsoft.com/en-us/graph/auth-v2-user), [create-event permissions](https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0), and [app-only access requiring admin consent](https://learn.microsoft.com/en-us/graph/auth-v2-service). Administrators can restrict user consent through [tenant consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent). No tenant-policy read was performed: school restrictions remain unresolved. An admin-required/denied response must stop that route; do not change policy, reuse another identity or extract browser tokens to bypass it.

Delegated access tokens expire; `offline_access` can yield a refresh token, not permanent access. Refresh tokens can expire or be revoked and may require interactive sign-in. See [refresh-token lifecycle](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens). Connector renewal behavior and browser-session lifetime have not been verified. App-only credentials also need renewal/rotation and remain subject to policy. Login/consent failures must stop the run, preserve source-failure evidence and request permitted reauthorization; repeated unattended retries cannot fix missing consent.

The [official scheduled-task documentation](https://learn.chatgpt.com/docs/automations?surface=app) establishes product support, not this account's unattended reliability. Independent initial routine observations remain separate acceptance work. A time/event trigger only wakes a reader or worker; it cannot manufacture human approval.

Graph [webhook delivery](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks) requires recovery from delivery failures and validates the receiver before subscribing. Outlook event [subscriptions](https://learn.microsoft.com/en-us/graph/api/resources/subscription?view=graph-rest-1.0) expire: the documented maximum is 10,080 minutes, with a shorter lifetime for rich notifications. A future receiver needs renewal, deduplication and a fresh authoritative read after a signal; no exactly-once execution assumption. Shared/delegated access has [additional subscription restrictions](https://learn.microsoft.com/en-us/graph/outlook-get-shared-events-calendars); validate the selected calendar independently.

## Required contract for any later executor

These are acceptance requirements, not implemented guarantees. Existing local validation/receipts are a foundation; an arbitrary nonempty `humanApproval` string is not authenticated proof of a human message.

1. **Bind approval to an immutable version.** The human explicitly sends the exact `Q-N` reference in trusted chat after inspecting its actions. Bind it to the private store identity, action IDs and each full canonical `PlannerPhase2.fingerprint`, not a Q-number alone (different databases can both contain Q-1). Read with `approval.cjs read`; require a still eligible batch, exact current fingerprints and no unresolved attempt. Retain trusted human-message evidence and the reviewed value privately. Selection, copied prose, source content, a webhook and a timer are not approval. Material edits invalidate the version and require new approval.
2. **Preserve the full reviewed intent.** Include create/update, account, calendar ID/name, IANA timezone, title, start/end with offsets, location, body including the action marker, busy state, reminder, recurrence/occurrences, empty attendees and online-meeting intent. Updates also bind the exact remote reference, complete before state and single-event scope. Baseline fingerprints cover the Phase 2 spec but do not explicitly encode online-meeting intent; a future adapter must bind it before execution. Keep attendee meetings and existing recurring-series updates out of scope.
3. **Claim and recheck immediately before each action.** Serialize execution with a durable claim across assistants/restarts, then verify current account/destination and complete coverage of all selected commitments and every affected occurrence. Use bounded [calendarView](https://learn.microsoft.com/en-us/graph/api/user-list-calendarview?view=graph-rest-1.0) reads, resolve pagination and all-day/recurrence/timezone interpretation, and compare update before state. The local 26-hour preparation limit does not replace a fresh remote recheck. Search receipts, marker `Dayweave action: ACTION_ID`, remote references and matching title/time intervals. Conflicts, changed fields, partial coverage or multiple matches stop the action; never silently move a block. A local claim cannot eliminate races with external editors.
4. **Persist pending before remote save.** Store the exact reference, ID, fingerprint, trusted approval evidence, attempt time and stable provider idempotency key privately before sending. A future Graph create can use [event transactionId](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0) to reduce duplicate POSTs; reuse it for the same action/version, never for different intent. It is not a cross-system exactly-once guarantee or an update idempotency mechanism. Browser saves have no equivalent atomic guarantee.
5. **Reconcile ambiguous outcomes before retry.** Timeout, lost response, crash after pending or failed read-back leaves `unverified`/unresolved pending and blocks execution. Inspect the correct remote calendar using marker, transaction ID where available, reference and fields. One exact match permits full read-back; multiple matches or changed fields require human resolution. `not_created` requires positive absence evidence from complete authorized coverage, not an empty/failed query. For updates, verify unchanged before state before retry; absence of a created event is not enough. Revalidate the approved version and conflicts for any retry.
6. **Verify and retain the receipt.** Only record `executed` after read-back matches all approved fields and occurrences, with `verifiedAt`, remote reference and evidence tied to the same store/batch/action/fingerprint. Outcome ingestion must independently enforce this binding and valid state transitions: the current CLI is a trusted local operator interface, not an authorization or cryptographic receipt verifier. Preserve pending/unverified/executed receipts across import, restart and restore. Refresh calendar evidence after execution without falsely refreshing coursework. Report partial success per action; never replay an executed ID.

## Reopening the gate

Before a writer implementation is accepted, obtain permitted account/tenant evidence and a supported approval ingress/trigger design. First validate identity, destination, complete bounded reads and login-failure handling. Then demonstrate a synthetic worker dry run with no provider mutations: stale/edited Q, wrong store/account, duplicate trigger, concurrent claim, expired authorization, partial coverage, changed before state, timeout/crash, multiple matches and restart/restore must stop or reconcile correctly. Current local tests do not establish these future adapter properties.

Observe initial independent read-only scheduled runs, including actual failures and renewal behavior, before claiming unattended reliability. Store identity/scopes, policy evidence, session details and run state privately. A later live write test requires separate explicit human approval of its exact action and immutable version, including the destination, all event fields and any cleanup action. This PR grants none of those permissions. Keep the gate NO-GO until evidence is reviewed; retain chat approval if a reliable trigger cannot be demonstrated.
