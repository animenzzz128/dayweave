# Snapshot contract (v1)

Use `examples/snapshot.json` as a complete synthetic reference. A snapshot is UTF-8 JSON, schemaVersion 1. All instants must use ISO 8601 with an explicit timezone offset or `Z`. `timezone` is the IANA display/planning timezone.

| Field | Meaning |
| --- | --- |
| `generatedAt`, `summary`, `coverageNote` | Collection time, daily summary, prominent limits |
| `courses[]` | Stable `id`, code, name, category, note, source URL |
| `assignments[]` | Stable `id`, courseId, course, title, dueAt/null, status, requirement, sourceId, source, evidence, description, materials, checklist, aiPolicy, estimateMinutes |
| `events[]` | Stable id, title, start, end, busy, location, sourceId, source |
| `proposals[]` | Stable id, title, start, end, calendar, recurrence, status, reason, source |
| `calendarCoverage` | Exact checked start/end, complete boolean, explanatory note; Google coverage adds provider identity ([below](#gmail-read-only-snapshot-and-google-calendar-identity)) |
| `priorities[]` | Up to three title/detail/source records |
| `sources[]` | Stable id, name, status, lastSuccess/null, note, optional source |
| `career` | enabled, source, tracks[], unknowns[], candidates[], roles[] |
| `email` | Optional read-only Gmail snapshot; missing means unknown, `{enabled:false}` means disabled ([below](#gmail-read-only-snapshot-and-google-calendar-identity)) |
| `questions[]`, `weeklyReview` | Uncertainties and review summary |
| `actionHistory[]`, `candidateHistory[]` | Durable records keyed by id |

Assignment status: `submitted`, `graded`, `excused`, `not_submitted`, or `unknown`. Requirement: `required`, `choice`, or `uncertain`. Submitted/graded/excused wins over urgency; choice requirements are optional opportunities; uncertainty goes to verification. Remaining deadlines classify as overdue, <=72h, <=168h, later, or undated.

Courses may carry `collection: {mode: "manual", scheduleUrl}` and `schedule` (`url`, `checkedAt`, `sessions[]` of `date`/`title`, and `changedAt`/`changes` after a change) for work outside Canvas. A course read from its own site API carries `collection: {mode: "site", url}` instead, its `schedule.sessions` also have `at` (the start time), and its assignments carry `siteSlug`; records the collector adds use ID `<code>-<slug>` and source `site-<code>`. Courses may carry `canvasCourseIds`, the Canvas sites (including merged sites) linked to them. Assignments may carry `canvasAssignmentId`, the Canvas assignment ID the cloud collector matches feed items by; records it adds use ID `canvas-<id>`, source `canvas`, status `unknown`, requirement `uncertain` and no estimate ([cloud collection](cloud-collection.md)). Source instructions (Canvas feed, course-site connector) fill an empty `description` only; a source status read (Canvas planner with `DAYWEAVE_CANVAS_TOKEN`, course-site submissions) replaces `unknown`/`not_submitted` and any read of `submitted`/`graded`/`excused` wins, but a read never turns those three back into `not_submitted`.

Source IDs link failures to records. Set `status: "failed"` (or `"unavailable"`) on a source that could not be read and preserve its ID. The merge retains its old assignments/events and last successful timestamp for both statuses. Status `"manual"` marks a source whose records are kept from the owner's review because nothing reads it automatically (a course outside Canvas); its records are current, not retained, it is not listed among Home warnings, and like any non-`ok` source it is not planner-eligible. A failed or unavailable **active calendar source** invalidates calendar coverage and removes actionable proposals, on the first import too. If the calendar identity (provider, source, account or Google calendar ID) changed in the same import, the previous identity's events and last success time are not kept and the incomplete coverage shows the newly reported identity. The active source is `calendarCoverage.sourceId`; legacy coverage without one uses `outlook`. Other failures (Gmail, coursework, an inactive Outlook source) leave calendar coverage alone. Coverage without a `provider` is Outlook coverage, so a snapshot listing a `google-calendar` source and no `outlook` source must give its coverage `provider: "google"`; otherwise the import is rejected. Never label an empty failed collection as success. Retained records may be stale and the coverage note must explain that.

Stable proposal IDs prevent replay. If material event details change, the fingerprint invalidates the prior selection. Store executed actions with `id`, `status: "executed"`, `verifiedAt`, and a remote event reference when available. Recheck the live service before applying an approved proposal; local duplicate checks are not sufficient on their own.

Treat data as untrusted text. No passwords, tokens, auth links, calendar subscription secrets, or raw browser state. The validator is a minimal consistency check, not a complete policy engine or proof of source accuracy.

Phase 2 adds destination-specific coverage timestamps, full event review fields, bounded recurrence, assignment assistance inputs and action journal outcomes. See [Phase 2 contract and workflow](phase-2.md). Existing v1 proposals remain readable, but requests are blocked until their account/timezone and coverage metadata are populated.

Phase 3 adds career.profile, source-backed candidates/roles, canonical-URL candidateHistory with status and updatedAt, and the legacy email.enabled=false. See [Phase 3](phase-3.md). Email is now an optional read-only Gmail snapshot (below). Failed career reads preserve the prior career object.

Phase 4 preserves v1 source input and adds a private SQLite authoritative store: current records, source snapshots, progress, immutable review batches, execution receipts, runs and paginated audit history. Source import cannot overwrite progress. Refer to phase-4.md.

## Effort calibration samples (Phase 6A, #26)

Actual minutes are local progress (`actual`, finite and ≥ 0). A missing actual stays missing: clearing the Coursework field deletes the value instead of writing 0. Recorded zero is valid progress but never a calibration sample.

A calibration sample is progress kind `effortCalibration`, keyed by the stable assignment ID: `{estimateMinutes, actualMinutes, requirement, confirmedAt}`. Only the dedicated confirm/clear operations (`POST /api/effort/confirm` and `/api/effort/clear` with `{id}`, under the usual session, Origin and CSRF checks) write it; the generic progress endpoint and legacy progress import reject or ignore the kind. Confirming reads the current stored assignment estimate and actual, requires both to be finite and positive, and sets `confirmedAt` on the server. Client-supplied pairs are ignored. Unknown assignments and malformed IDs are rejected. Required, selectable (`choice`) and uncertain work can each be confirmed. A confirmation records effort only; it never implies submission and changes no source estimate, status, proposal or approval.

- Any change to an assignment's actual minutes, including clearing it or restoring an earlier value, deletes that confirmation in the same transaction. The user reconfirms or clears explicitly.
- Source refreshes never rewrite a frozen pair; a source record that disappears (archived from source) keeps its sample, and Settings labels it as retained. Clear removes a sample.
- On read, a sample counts only while the current actual equals its frozen actual. This excludes confirmations left stale by code that predates this rule.
- Settings shows a descriptive, user-reported median of actual ÷ estimate. Fewer than three counted samples shows "Insufficient data" with the count. Exclusion counts cover unconfirmed actuals, zero actuals, actuals without a positive estimate, stale confirmations and malformed samples. Nothing adjusts estimates or plans.
- Samples are ordinary progress rows. JSON export includes them one way; there is no JSON import for samples. SQLite backup/restore round-trips them. No schema `user_version` change and no backfill of earlier actuals.

## Workload modes (Phase 6B, #27)

Home has an explicit, advisory focus mode: `standard` or `reduced`. It is stored as progress kind `preferences`, ID `workloadMode`, and written only by `POST /api/workload-mode` with `{mode}` under the usual session, Origin and CSRF checks. Any other value is rejected before a write. The generic progress endpoint and legacy progress import reject or ignore the kind. A missing or malformed stored value reads as `standard`, so older databases open in Standard. Source refreshes and restarts keep the preference. JSON export includes it, and restoring an older SQLite backup restores that backup's mode.

- Standard keeps the original Home overview.
- Reduced lists required work that is overdue or due within 72 hours first, ordered by deadline and then stable ID. Other required work (later or undated) and selectable (`choice`) work stay listed and labelled, and Coursework is unchanged.
- Focus lists apply this precedence; the first match wins:
  1. Submitted, graded or excused work is left out of every focus list and never returns to urgent, even when its source failed or is unavailable. That source's failure still shows in the data-health warnings in both modes, and Coursework History still tags the record `verify`.
  2. Other work from a failed or unavailable source goes to verification.
  3. Selectable (`choice`) work is listed as selectable and is never urgent or required. If its submission status is unknown, it keeps that listing with a "Submission status unknown" tag and is also listed in verification.
  4. Uncertain requirements, unknown submission status and a missing requirement go to verification, not to a definite category. Exception (owner decision 2026-10-27): an assignment with `statusUnread: true` (its source cannot report submission, such as the Canvas feed without a token) keeps status `unknown` but is listed by its due time and shows a "Status not read" tag instead of entering verification.
  5. Remaining required work is urgent (overdue or due within 72 hours) or other required work.
- Work archived locally in Coursework stays in the focus lists, tagged "Archived locally". Its link opens Coursework History, where the record is listed. Following the link changes no archive state.
- **Local marks and Past due (new front end, 2026-10-24).** Coursework can mark work you did or do not need to do: progress `archive[<assignment id>]` is `{"status":"done"|"skipped","at":ISO}` (legacy `true` reads as done; `null` clears it; anything else is refused). A mark never changes the source record, survives refreshes and keeps the work out of the planner. Marked work and source-submitted work are listed under Done. Work that is neither, with a due time more than 3 days ago, leaves Today and the other tabs for Coursework → Past due; nothing is deleted and it can still be marked. In the new front end, marked and past-due work is left out of Today's focus lists (the classic UI rule in the previous item is unchanged).
- Both modes always show verification items, non-ok sources, a stale snapshot and calendar coverage limits. Blank calendar time is never treated as free capacity.
- Switching changes only the preference row and an audit entry. It changes no source records, estimates, proposals, approvals, Q-numbers or effort samples, and it never authorizes calendar, message or submission actions. Nothing is scheduled automatically.

## Career feedback ordering (Phase 6C, #28)

The Career Roles and People tabs order each list by the user's explicit status on that item, keyed by the item's canonical URL (or stable ID without one). The status is the latest `career` progress or `candidateHistory` record, as before. No new progress kind, endpoint or schema change.

- `saved` items come first and show "Saved by you". `dismissed` items come last, stay visible with Restore, and show "Dismissed by you". Every other status (including restored, `reset`) keeps the source order. Ties keep source order, so with no feedback both lists match the source order exactly.
- Roles and People are ordered separately. Follow-ups and History keep their existing order.
- Existing exclusions stay: applied roles; pending, connected and contacted people; source-removed people; and source-removed roles unless saved. A saved role removed from the source stays first and is labelled "Removed from latest source; retained". Dismissed items no longer leave Roles/People, and they also stay listed in History.
- Only each item's own status counts. Nothing is learned or inferred for other roles or people, editorial scores are not used, and no model is trained.
- Ordering changes presentation only. Source records, evidence, requirements, eligibility gaps and unknowns, relationships, proposals, approvals, effort samples and the workload mode are unchanged. Saving never makes unknown eligibility eligible.
- Eligibility checks are unchanged and skip what the profile cannot support: with no `usSponsorshipRequired` (or no profile) there is no US sponsorship gap, and when neither role nor profile has a `startYear` there is no start-year gap. The Career page labels these instead. Roles shows a "Profile facts missing: … — eligibility for these is not assessed and is not shown as eligible" banner when the profile is missing, null or lacks `usSponsorshipRequired`, `startYear` or `workEligibility`. Affected role cards show "Eligibility not fully assessed" and name each unassessed check on the eligibility line. This applies to US roles without confirmed sponsorship, and to roles where neither role nor profile states a start year. These labels never mean eligible. Saved/dismissed/reset does not change them, and they do not appear with a complete profile. The legacy static page does not show them.
- Source refreshes and failed career sources keep each item's state: the baseline is the current (or retained) source order, and the user's status follows the canonical URL.

## Weekly evidence trends (Phase 6D, #29)

Settings → Weekly trends compares two explicitly dated weeks from retained source snapshots. It is read-only: `GET /api/trends` (optional `week`) runs under the usual local session checks, writes nothing, and has no write route.

- An observation is one retained `source_snapshots` row (the merged snapshot stored at import). It belongs to the week of its source `generatedAt` (collection time) in the current snapshot `timezone`. Weeks run Monday 00:00 to Sunday 24:00 local time. Boundaries are calendar dates, so DST changes cannot shift them. Import time (`importedAt`, the row's `at`) is shown separately and never used for bucketing. Rows recorded with another timezone are still placed by the current one and noted.
- By default the page shows the week of the latest `generatedAt` among the 1,000 most recent retained imports, and the week before it. `week` must be the Monday that starts a week, no later than the current week and at most 12 weeks earlier. Any other parameter, a repeated `week`, an invalid date or a week outside that range returns 400. Before validation the server makes two bounded, read-only reads (the snapshot timezone and the retention summary); the range query never runs for a rejected request. Without a valid snapshot timezone the range is undefined, so the page reports trends as unavailable (200, `available: false`) for any well-formed `week`, while malformed parameters are still rejected with 400. The current week is labelled "In progress · partial week".
- Repeated imports with the same `generatedAt` and the same projected content count once. The projection is source statuses plus each assignment's ID, requirement, status, source and archived flag. Each week shows how many duplicate imports it collapsed.
- Counts come from the latest observation in each week. Required work (`requirement: "required"`) is counted by status: submitted/graded/excused, `not_submitted`, `unknown`, and other or missing status. Unknown status is never folded into submitted or not submitted. Selectable (`choice`) work and uncertain or missing requirements are listed separately and are not required work.
- Only records from a listed source whose status is not `failed` or `unavailable` count as fresh. Three kinds of record are counted separately under "Not counted as fresh": records from a failed or unavailable source (a failed source's earlier records are retained by the merge; an unavailable source's records are only not fresh), records with `archivedFromSource: true`, and records whose `sourceId` is not listed. If an observation has no fresh records and has a non-ok source or such records, its counts read "No fresh observations", not 0.
- Source health per week lists each source with how many observations reported it ok, failed or unavailable, with another status (such as `partial`), or not at all, plus its status in the latest observation.
- A week without observations shows "No observations" for every value, never 0, and is never filled from a neighbouring week.
- A comparison needs all of the following:
  - both weeks have observations and neither latest observation lacks fresh records;
  - no observation in either week has a non-ok source or unlisted-source records, and every source of a week is reported in each of its observations;
  - the latest observations of the two weeks list the same sources (a source omitted entirely archives its records, so counts would drop for coverage reasons alone);
  - every retained import collected in either week was read;
  - neither week reaches the retention horizon;
  - the read was not truncated.

  Otherwise the page says "Not comparable · coverage limited", lists the reasons and shows no change, so a lower count caused by a failed source never reads as an improvement. Comparable changes are descriptive; nothing is labelled better or worse.
- Retention is unchanged: snapshots are kept 30 days and pruned only when a new import runs. The horizon is the latest import time minus 30 days. A week that starts on or before the horizon's local date is labelled "Coverage incomplete". An empty week there means evidence may have been pruned, not that nothing happened. With no retained snapshots, coverage is unknown.
- The read is bounded. `Store.snapshotObservations({from,to,limit})` takes ISO instants with an explicit offset and a limit of 1–1000. It returns rows imported in `[from, to)`, oldest first, projected to the fields above, with a `truncated` flag. Trends read from two days before the earlier week with a 500-row limit; a truncated read is labelled and is not comparable. A row whose `generatedAt` is more than about a day after its own import time can fall outside that read. Each week therefore compares the number of retained imports collected in it (from the `generatedAt` of the 1,000 most recent imports) with the number actually read. When some were not read, the week is labelled "Coverage incomplete · … not read" and the pair is not comparable. If none were read, the week says "No observations read" instead of "No observations", as it does for every empty week when the read was truncated.
- "No observations" is bounded, not absolute. It means the 500-row read was not truncated and returned no row for that week, and none of the 1,000 most recent retained imports was collected in it. Imports older than those 1,000 that were also imported before the read window are checked by neither bound, and pruned snapshots no longer exist. "No observations" is therefore missing data: coverage of that week is unknown. It is not proof that nothing was collected, and it is never a count of zero.
- No effort, completion time or work session is shown or inferred. Cumulative actual minutes are not weekly effort, and progress timestamps are not completion dates. Source records, requirements, proposals, approvals, Q-numbers, effort samples, the workload mode and career statuses are unchanged. There is no schema `user_version` change and no new runtime dependency.

## Gmail read-only snapshot and Google Calendar identity

Dayweave has no OAuth client, token store or mail/calendar network access. An authorized assistant's existing Gmail and Google Calendar connectors collect a snapshot ([collection procedure](google.md)); the web app shows **the last collected snapshot**, labelled with its collection time, never as live access. `examples/google-snapshot.json` is a complete fictional Google-only reference with no Outlook source.

### `email`

- **Missing** means unknown: the Email page says "Status unknown" and never shows an empty inbox. **`{enabled:false}`** (legacy snapshots) means disabled. `enabled` must be the boolean `true` or `false`; any other value rejects the import.
- An enabled record has `provider: "google"`, `account`, `sourceId` (listed in `sources[]`), `checkedAt` (explicit offset), `capabilities`, `request`, `coverage` and `messages[]`. `lastSuccess` and `retainedFrom` are maintained by the merge.
- `request` records the exact `query`, `windowDays` (1–7), `limit` (1–50) and the `from`/`to` instants of the window. The selected default is the `Yale` label (school mail forwarded into Gmail) for the last seven days, at most 50 messages; the query is free text, so older snapshots that read the inbox stay valid. The limit applies to the messages returned by one read; retained messages from earlier reads are listed in addition and labelled, so the page can show more than 50.
- Mail is read-only. `capabilities.read` cannot be false; `send`, `delete`, `labels` and `modify` must be false or absent and are stored as false. Read access never implies send capability.
- `messages[]`: stable `id` and `threadId`, `receivedAt` (explicit offset, inside the requested window), `from`, `subject`, `snippet`, `labels` (≤20), `unread`, `hasAttachments`, `attachmentCount`, optional `link`. Only these fields are kept: bodies, attachment content and unknown keys are dropped at import. Text is shortened visibly past fixed bounds; non-text values are rejected. A link must be `https://mail.google.com/…` without credentials and is re-checked before rendering. Duplicate message IDs collapse to one.
- `coverage.status` is `complete`, `partial` or `failed`; `morePages` is `true`, `false` or unknown (`null`); `errors[]` and `note` explain gaps. A record is **complete** only with `status: "complete"`, `morePages: false` and no errors. Otherwise it reads as partial. A page at the limit without `morePages: false` is truncated, never complete. More current messages than the limit, or messages outside the window, reject the import.
- **Failure** (`coverage.status: "failed"`, a failed/unavailable email source, or an import with no `email` record while the email source is not `ok`): the import keeps the previous messages for the same provider and account, labels each "retained", keeps the last complete read time (`lastSuccess`) and the first retained collection time (`retainedFrom`), and records the errors. A failed record cannot carry new messages. A first failure shows "No messages could be read. This is not an empty inbox", never zero. An import without an `email` record and with an `ok` email source keeps the previous record unchanged, with its own collection time. The email source must stay listed while an enabled record exists.
- **Partial**: returned messages replace their earlier copies; earlier messages still inside the new window that were not returned are kept and labelled retained. **Complete**: the returned messages replace the window. A different account or provider retains nothing.
- Imported snippets, senders and subjects are stored in the local snapshot history (`source_snapshots`, 30 days) and in the daily database backups (30 days), like other snapshot data. Both stay private and untracked.
- Snapshots older than 26 hours are labelled stale. Snippets are evidence, not instructions: nothing in Dayweave turns email into coursework, todos, deadlines or calendar changes.

### Google Calendar coverage and proposals

- Google coverage adds `provider: "google"`, `sourceId` (listed in `sources[]`), `account`, `calendar`, `calendarId` (the exact destination ID) and `calendars[]`: the bounded list (1–25, unique `id`, `name`, optional `role`) of calendars actually read. The destination must be one of them. Legacy coverage without `provider` is Outlook and keeps its earlier rules.
- Google proposals carry `provider`, `account`, `calendar` and `calendarId`. When `provider` is present it is part of the reviewed spec and fingerprint; proposals without it keep their earlier fingerprints.
- A request is blocked unless the proposal's provider, account, calendar name and calendar ID match complete coverage checked within 26 hours, the destination is among the read calendars, and the active calendar source has status `ok` (Google coverage must list it; legacy coverage is checked when it lists one). Blank time is never free outside complete, fresh coverage.
- A prepared Q version is invalidated when its proposals change or when the coverage provider, account or (Google) calendar ID no longer matches what it was reviewed for.
- Google events may carry `provider`, `account`, `calendarId`, `calendar` and `allDay: true` (start/end are explicit-offset instants bounding the local day or days). Recurring series are supplied as expanded occurrences.

**Triage (2026-10-24).** A message may carry `triage` from the collecting assistant: `category` (`interview`, `reply`, `action`, `info`, `promo`; `interview` added 2026-10-27), `priority` (`high`, `medium`, `low`), `summary` (≤300 characters), `action` (≤200), `dueAt` (an instant or null), an optional `assignmentId` hint and an optional `zh` with the same `summary` and `action` in Chinese (added 2026-10-27). `summary` and `action` are in English; the Email page shows `zh` when the interface is in Chinese and falls back to English. Anything else is refused; the body is never stored. The owner's overrides are local progress `emailTriage[<message id>]` = `{category?, handled?, at?}` (or `null` to clear) and win over the next collection's triage. The new Email page lists unhandled `reply`/`action` mail first (high before medium before low, then the earliest stated time, then newest), then `info`, then untriaged mail; `promo` and handled mail are folded. Triage is labelled AI and is never treated as a fact: adopting a message as a todo only prefills the form.

## Todos and daily plan recommendations

### Todos

Coursework → Todos holds your own tasks as progress kind `todo`, written only by `POST /api/todos/save` and `/api/todos/complete` (usual session, Origin and CSRF checks); the generic progress endpoint and legacy progress import reject or ignore the kind. A todo is `{id, title, dueAt, durationMinutes, notes, status: "open"|"done", origin, createdAt, updatedAt, completedAt, version}`.

- Every planning input is explicit. `dueAt` must be sent: an instant with an offset or `null` for "No due date". `durationMinutes` is a whole number from 5 to 600. Nothing is inferred.
- Editing bumps `version`. Editing or completing a todo removes its never-attempted planner blocks, which invalidates any prepared Q version containing them. At most 200 todos can be open, including by reopening a completed one. Completing a todo never changes a started block; Timetable flags a started block whose todo was later marked done so you can reconcile it in chat. Creating, approving or executing a block never marks work done.
- **Adopting an email** (Email → "Adopt as todo…") is the only route from mail to a todo. You confirm the title, due date and duration. The origin records the message ID, thread ID, account, subject and received time taken from the stored snapshot, never from the request, and the message must be in the current snapshot. One open todo per message. A disabled or missing email record cannot be adopted. Nothing creates coursework, required work or deadlines from email.

### Daily plan recommendations

Timetable (day view) → "Generate recommendations" calls `POST /api/plan/generate {date}`. Only this explicit action plans; imports and page loads never do. The planner (`src/planner.cjs`) is deterministic for the same snapshot, todos, local archive/dismissals, date and clock.

- **Gate.** It plans only with Google coverage that is complete, checked within 26 hours, covers the whole planning window (09:00–24:00 local by default) of the date, and whose active source is `ok`, with a destination account and calendar ID. A recurring series that was not expanded is a gap. Any gap means no blocks, and every candidate is listed as not planned with the gap shown.
- **Candidates.** Required coursework with `status: "not_submitted"` (or `unknown` with `statusUnread: true`, owner decision 2026-10-27: its blocks say the submission status was not read and to remove them once submitted) and a positive `estimateMinutes` from an **eligible source**, plus open todos. A source is eligible only when it is listed in `sources[]` with status `ok`, the snapshot was collected within 26 hours (the same staleness rule as Data Health) and the source's `lastSuccess`, when given, is within 26 hours. Partial, failed, unavailable, unlisted and stale sources are not eligible. Choice work, uncertain requirements, unknown submission status, ineligible sources, missing estimates, local archives and passed deadlines are listed as not scheduled with a reason. A deadline before the chosen day's 09:00 start says so; only a deadline before now says it has passed. Submitted/graded/excused and source-removed work are left out. Recorded actual minutes are not subtracted.
- **Busy time.** Every event with `busy !== false`, including all-day events and expanded recurring occurrences, plus every occurrence of every kept proposal (other dates, collector proposals, started blocks), blocks time. Kept proposals are expanded with the same recurrence rules as requests; a proposal that cannot be expanded is a gap and nothing is planned. Free (`busy: false`) events do not.
- **Started actions are canonical protections.** A pending, unverified or executed action keeps blocking its time and covering its work even when the snapshot lost the proposal (calendar failure, restore, refresh). Only a copy whose fingerprint matches the frozen receipt counts: the store's approval copy first, then the snapshot copy. A stale same-ID copy (an older backup, or a collector or local edit from before the action started) never does. Imports and restores put the receipt-matching approval copy into the snapshot, replacing a stale same-ID copy and re-adding a dropped one whose time is not over, so Timetable, Review, request checks and planning all see the reviewed time. A pending or unverified receipt with no matching copy makes the time unknown: nothing is planned and no proposal can be requested until it is reconciled; no copy is invented. Request checks reject any proposal that overlaps an occurrence of a started action, except that an update may overlap the executed create of its own target (same receipt `remoteRef`). An executed receipt without a matching copy is protected only by its calendar event once a later read imports it.
- **Placement.** Earliest deadline first (undated last, then kind and ID). Work is split into blocks of at most 90 minutes, as even as the 5-minute grid allows. Blocks keep 15-minute rest gaps around busy time and other blocks, never start before now, end by the deadline and by 24:00, and the reserve holds across repeated generation: usable minutes are the day's remaining minutes minus other busy events, and minutes already allocated to kept or started proposals on that day count against the 80% budget (`budget = floor(0.8 × usable) − already allocated`). A calendar event that is a started action's own event is an allocation, not lost capacity, so the reserve keeps its base after pending → executed → refresh. An event is own when it carries an executed receipt's `remoteRef` (as its `remoteRef`, its `id` or its `calendarId/id`) in the copy's account and calendar (the destination when no copy survives), or when it exactly matches an occurrence of the receipt-matching copy (title, calendar, start and end; one event per occurrence). Events on other calendars or with other titles at the same time stay busy and reduce usable time. Own time is counted once. Mid-day generation uses the time remaining after now as the base. Each block must also pass the normal request checks. Work that does not fit is listed as not scheduled or partly planned with the reason.
- **No double scheduling.** Minutes already covered are subtracted: every occurrence of a started action (approval or snapshot copy), the occurrences of unstarted kept proposals that have not ended yet (a past unstarted block covers nothing), attempted receipts that record `sourceRefs` and `minutes`, and collector proposals whose `source` equals the assignment's source URL. Fully covered work is listed as already covered.
- **Calendar colour (2026-10-28, owner request).** Each block carries `color`, a Google Calendar `colorId` (`"1"`–`"11"`) by what it is for: coursework `9` (Blueberry), quiz and exam review `6` (Tangerine), interview preparation `11` (Tomato), todos `5` (Banana). A weekly goal uses its own optional `color` from planning settings, else the default for its recommended ID (Gym `10` Basil; Job applications and LinkedIn connect `3` Grape), else `2` (Sage). `color` is part of the fingerprint when present (blocks without it keep their fingerprints) and is written as the event's `colorId`; the read-back must show the same colour. Proposals without `color` keep the calendar's default colour.
- **Not-planned groups (2026-10-28).** Each not-scheduled item carries `group`: `action` (needs the owner: no estimate, a source problem, unknown status, no free slot, a passed deadline), `later` (review or paced work whose start day, `startsOn`, has not come) or `hidden` (archived locally, choice work, already covered, spread, over the daily limit, or due before the day). The Plan page lists `action` first, folds `later` by start day and does not show `hidden`.
- **Deadline risk (2026-10-28).** `planner.risks` lists required work, review and todos due within the next 7 days whose planned minutes before the deadline (non-dismissed blocks that end by it and are started or still ahead, plus attempted receipts without a copy) fall short of what it needs. Plan and Today show the list; it reads the snapshot only.
- **Week approval (2026-10-28).** Besides one day at a time, the Plan page can prepare one Q version with every open, passing block of the next 7 days.
- **Rewriting written blocks (owner request 2026-10-28).** Generating a day (`Store.planDay`, so automatic drafts too) treats that day's planner blocks that were written (`executed` receipt with a `remoteRef`), have not started, were not edited by the owner (an approval lock, `lockedBy: "approval"`, does not count as an edit) and that the latest calendar read still shows exactly as written, as free again. The planner places the work again; a written block keeps its time when that time is still free for the same work and length, so it keeps its ID and nothing changes. Every other such block gets a removal: a proposal with `action: "delete"`, `replaces` (the written block's ID), `remoteRef`, the same title and time, and a stable ID per event (`plan-<date>-rm-<hash>`). While a removal stays (not dismissed), the block it replaces no longer holds time or covers work, and its calendar event is ignored by the checks. Skipping (dismissing) a removal keeps that block for good. A removal cannot be edited. Approving the day or week puts the removals and the new blocks in one version ("N new / M removed"); [direct writes](google-direct.md) run the removals first.
- **Output.** Blocks are ordinary `create` proposals with `origin: "planner"`, `planDate`, `provider: "google"`, the coverage account/calendar/calendarId, no attendees, `recurrence: "One time"`, `busy: true`, a reason and `sourceRefs` (todo ID and version, or assignment ID, due date and estimate). IDs hash the content, so identical blocks keep their ID and changed blocks get new ones. The plan explanation (gaps, assumptions, usable/budget/allocated minutes, not-scheduled reasons) is stored as progress kind `plan` for the date and kept 30 days. At most 100 not-scheduled items are stored, with the full count (`unscheduledTotal`).
- **Locked blocks (2026-10-27).** Editing a planner block (`POST /api/proposals/edit`) sets `locked: true`; `{locked:false}` alone unlocks it. Generating also locks the blocks of every prepared version the owner approved (`locked: true`, `lockedBy: "approval"`), so regeneration cannot invalidate an approval before the write; an edit drops `lockedBy`. Blocks locked by an approval before 2026-10-28 carry no `lockedBy` and are treated as edited. Locked blocks are kept like other kept proposals: they occupy time and cover work. `locked` is not part of the fingerprint.
- **Automatic drafts (2026-10-27; a rolling week from 2026-10-28, owner request).** After each successful `POST /api/ingest`, the server generates today (the time left) and the next six days and returns `plans: [{date, ready, blocks, gaps}]`. A day that cannot be planned (a gap such as incomplete coverage, or a day past the checked calendar window) keeps its blocks; only an explicit generation clears them.
- **Several days at once.** `POST /api/plan/generate {date, days}` (1–7 days from `date`; the Plan page's "Plan the next 7 days" button) returns `{days: [{date, ready, blocks, gaps}]}`. It first clears the replaceable drafts of every day in the range, then plans the days earliest first in one transaction, so old drafts on later days never count as coverage and each day sees the new blocks of the days before it (pacing and "already covered" carry over). Without `days` the route plans one date and returns that plan, as before.
- **Regeneration** replaces that date's never-attempted, unlocked planner blocks; changed blocks invalidate their prepared versions, and pending/unverified/executed blocks stay. **Imports** keep unstarted planner blocks only while the coverage provider, account and calendar ID match, each referenced assignment is still required, not submitted, from an eligible source, not archived locally and has the same due date and estimate, and the block has not ended. Archiving an assignment locally removes its unstarted blocks at once. Started blocks are always kept. A failed or unavailable calendar source removes all unstarted proposals but keeps started ones (they stay non-actionable), and a collector proposal with a started action's ID never replaces its reviewed fields. A restore puts started actions back from their receipt-matching approval copies in one transaction with the preserved receipts and approvals; on failure the pre-restore database is put back. Started planner blocks are kept indefinitely (no retention limit yet).
- Requests now allow a block to end exactly at local midnight; nothing may start before 07:00 (the sleep window, changed from 09:00 on 2026-10-27) or run past midnight.
- **AI estimates (2026-10-27).** An assignment may carry `estimateSource: "ai"`, `estimateBasis` (≤300 characters) and `estimateFor` (a hash of the instructions it was made from), and `checklistSource: "ai"`, written by the collection build from the task's `estimates.json` ([cloud collection](cloud-collection.md)). They fill only an empty or earlier AI estimate, change only when the instructions change, and are shown as AI estimates. The planner uses them like any estimate.
- **Planning settings (2026-10-27).** The owner's rules are stored in `meta.planSettings`, apart from the snapshot, so imports never touch them; `POST /api/plan/settings` saves them (validated by `planner.planSettings`) and `/api/snapshot` returns them as `planSettings`. Until the owner saves rules, the recommended ones apply (`planner.RECOMMENDED`): day 09:00–24:00, lunch 12:00–13:00 and dinner 18:00–19:00 kept free, and weekly goals Gym (3 × 60 minutes, weekdays 07:00–09:00 or 17:00–19:00), Job applications (4 × 60, weekdays 13:00–18:00) and LinkedIn connect (5 × 30, weekdays 14:00–18:00). Day start is at least 07:00 and the day at least two hours; at most 6 breaks and 12 goals; a goal has a unique short ID, a title, 15–240 minutes per session, 1–14 sessions per week, allowed weekdays (1 = Monday), one to three windows from 07:00 of which at least one fits a session inside the planning day, at most `perDay` sessions a day (1–3, default 1; `perWeek` may not exceed allowed days × `perDay`) and an optional calendar `color` (`"1"`–`"11"`). An optional `maxDailyWork` (60–720 minutes in steps of 15) caps the coursework minutes (assignments, review and todos, counting kept blocks) planned on one day; work over it goes to other days. Interview preparation and weekly goals are not counted. Breaks are free time that blocks placement. The planning day bounds every block (owner decision 2026-10-27): only the part of a goal's window inside it is used. A refused save stores nothing, so the page checks the rules with the same `planner.planSettings` before saving, explains a goal whose sessions per week exceed its ticked weekdays × `perDay` (ticked weekdays, not the seven planned days) and keeps Save off until the rules hold; saving then plans the next seven days again with them (audit 2026-10-28). Blocks the owner edited or approved are not moved by new rules: the plan summary lists them as `held` (`id`, `title`, `start`, `end`, `why` `edited` or `approved`, and `outside` when they now fall outside the planning day or in a break). Day views draw from the saved day start, or from the hour of an earlier event or block that day.
- **Order (2026-10-27).** Interview preparation first, then work due within 72 hours, then weekly goals, then everything else by deadline. A goal counts the sessions of this Monday–Sunday week already in kept or started blocks (`sourceRefs` kind `habit`) and spreads the sessions still owed evenly over the allowed days left: session i goes on day floor((i + 0.5) × days left ÷ sessions left), so three sessions from Monday land on Monday, Wednesday and Friday. A day takes at most `perDay`. A session that does not fit is owed again on the next allowed day, and the reason is listed.
- **Pacing (owner decision 2026-10-27).** Work due after the 72-hour window is spread over the days from the planned day to its deadline day: at most `max(60, remaining minutes ÷ days left)` (rounded up to 5) on one day, counting that day's kept blocks, and none until the deadline is within twice the days it needs at 60 minutes a day (`2 × ceil(remaining ÷ 60)`). The not-scheduled list says which applies. Work due within 72 hours, review and interview preparation keep their own rules.
- **Quiz and exam review.** Required work whose title names a quiz gets 60 minutes of review in the 2 days before it; an exam or midterm gets 240 minutes over the 5 days before, at most 120 a day. Review needs a valid date but not a known submission status (an in-class exam has no online submission); submitted, graded or excused work gets none. Blocks are titled `Review: <title>` and refer to the assignment.
- **Interview preparation.** An email message whose category is `interview` (collector triage or the owner's override) and that is not marked handled gets 120 minutes of preparation before the interview time in `triage.dueAt` (at most 120 a day), or 60 minutes when no time is stated; a passed interview gets none. Blocks are titled `Interview prep: <summary>` and refer to the message (`sourceRefs` kind `email`). This is the one route from mail to the plan, and it only proposes blocks: writing them still needs an approved Q version.
- Generating writes local proposals only. Blocks still need selection, an immutable Q version and explicit chat approval before any calendar write.

## Career tracker

Progress kinds `careerJob` and `careerContact` (src/career.cjs) are written only by `POST /api/career/save` (`{kind:'job'|'contact', record}`) and `POST /api/career/remove`; `/api/progress` refuses them. Both are returned with the rest of `progress` by `/api/snapshot`.

- A job needs a title and a company. `stage` is one of saved, preparing, applied, assessment, interview, offer, rejected, withdrawn; `market` US/CN/HK/SG/Other; `track` ai-pm/strategy/operations/consulting/other (owner order: AI product, strategy and operations first, consulting second); `channel` website/referral/recruiter/linkedin/boss/campus/other. Dates (`deadline`, `nextDate`) are calendar days. `appliedAt` is set the first time the stage reaches applied or later and never moves. Every stage change and `event` note is appended to `timeline` (last 100 kept).
- A link that matches another job's link without query and anchor is refused. Removing a job unlinks its contacts; the audit log keeps the removed record.
- The first `/api/snapshot` (or career write) after a snapshot exists copies `snapshot.career.roles` and `candidates` into the tracker once (meta `career-migrated`), skipping items the owner dismissed and keeping applied/contacted marks. Later collections never re-add them.
- `careerSettings/main` (`POST /api/career/settings`, refused by `/api/progress`): `watch` (up to 60 `{ats, slug, company, market}`, `ats` greenhouse/lever/ashby/smartrecruiters, `slug` the board short name; duplicates folded), `keywords` (up to 40) and `sources` (source id → in use). The source catalogue itself is static (web/src/data/careerSources.ts).
- A stage records what the owner did. Dayweave never applies, sends a message or signs in to a job site.

## Approved Google Calendar execution

Procedure: [root writes](google.md#approved-google-calendar-writes-root-procedure), [direct writes from the hosted site](google-direct.md) (`POST /api/calendar/write`, the owner's sealed Google consent in `google_tokens`) and the [calendar executor](cloud-execute.md). The web app prepares immutable Q versions and, signed in, records the owner's approval of one (`owner_approvals`: approval id → `{channel:"web", text:"Approve Q-N", at, by}`, kept across restore with the approvals; withdrawn only before any receipt). No page route records receipts. Receipts come only from the bridge (`src/google.cjs`): through the local operator tool (`scripts/google-calendar.cjs`, chat approval) or the executor API (`/api/execute/*`, its own bearer secret, owner approval read from the database, never from the caller). The legacy `scripts/approval.cjs record` and `scripts/record-action.cjs` refuse Google receipts, and `A.record` accepts a Google outcome only from the bridge's read-back or reconcile. These are in-process consistency guards for the documented paths, not an authentication boundary: code or a person with local access can still call the modules or edit the private database directly.

- **Imported receipts.** A snapshot's `actionHistory` cannot add Google receipts. An import (`Store.importSnapshot`, so `scripts/db.cjs import`/`migrate`, and the legacy `render.cjs` merge) is rejected, with nothing written, when an incoming receipt the local journal does not hold:
  - names a provider other than Outlook, or carries a field only Google receipts have (`idempotencyKey`, `store`, `connector`, `account`, `calendarId`, `sourceRefs`, `minutes`, `hold`, `holdScope`, `conclusion`, or a structured `humanApproval` object), under any coverage;
  - belongs to a Google proposal in the old or incoming snapshot, a Google receipt or a Google approval copy;
  - or, while the local or the incoming coverage is Google, belongs to anything but an Outlook proposal already in the local snapshot. A proposal arriving in the same import never vouches for its own receipt, and an Outlook-shaped incoming coverage does not lift this.

  Omitting `provider` therefore does not help, and a forged receipt cannot bring planner allocations (`sourceRefs`/`minutes`) or a remote reference into a Google database. Receipts the journal already holds always win: an imported copy (for example an `executed` copy of a local `pending`) is ignored, so re-importing an export of the same database is a no-op. Legacy receipts in the Phase 4 shape (reference, id, status, times, fingerprint, remote reference, evidence, text `humanApproval`) still import while both coverages are Outlook, and under Google coverage only for an Outlook proposal already stored locally; that legacy path trusts the file. A database's receipts move only by backup and restore; an export imported into another database is rejected while it carries Google receipts. Restore keeps the current receipts and also brings back receipts that exist only in the backup file: a backup is trusted local data, so a foreign database file placed in `backups/` could add receipts. Like direct database access, that is outside these guards.

- **Spec.** `sourceRefs` (when present) join the reviewed spec and fingerprint, so a version is bound to its source todo/assignment as well as provider, account, calendar ID and every event field. Google actions must be `create` (or a planner removal, run only by direct writes, see above), one time, timed and attendee-free; requests are blocked otherwise.
- **Destination.** `calendarCoverage.calendars[]` entries may carry `accessRole`; a Google write needs the destination recorded as `owner`.
- **Connector profile.** Actions map to the connected create tool's arguments (`calendar_id`, `title`, `description`, `start_time`, `end_time`, `timezone_str`, `transparency`, `reminders`, `location` when non-empty) with `attendees: []`, `add_google_meet: false` and `event_type: "default"`. No invitation-update setting, client event ID or extended properties exist there, and none is claimed.
- **Store identity.** Each private database has a random `storeId` (meta, created once, kept across restore). The idempotency key is `d0` + 30 hex characters of SHA-256 over store ID, action ID and fingerprint, written only into the description marker. Pending freezes the store and key in the receipt; later states copy them instead of recomputing, and an outcome must be recorded in the same store.
- **Pending (Google).** `humanApproval` must be `{channel: "chat", text, at}` where the whole text is exactly "Approve Q-N" (any case, optional final `.` or `!`) and `at` is not before the version was prepared or in the future. Negations, conditions and other wording are rejected. The proposal must still pass the request checks and the create-only scope. The tool also requires a passing verify and a live re-read at most 15 minutes old. The pending claim is checked again inside the database write, so a second claim fails.
- **Live re-read.** One read per queried calendar (`reads[]` with `calendarId`, `complete`, raw `events`); calendar provenance comes from the query. Events with unreadable times or unexpanded series make the read fail closed; a marked event with unreadable times is still returned as a marked event. A marker on the destination is a duplicate, a marker on another calendar is a possible wrong-calendar write, and an unmarked same-title, same-time event on the destination is a possible duplicate; each stops the write.
- **Receipt fields.** For Google, the receipt carries the reference, fingerprint, provider, account, calendar ID and name, title, start, end, `sourceRefs`, `minutes`, `idempotencyKey`, `store`, `connector` (profile name) and `humanApproval`. These are derived from the approved proposal at pending, not from the receipt file, and frozen for later states. Outcomes keep the earlier states in `attempts` (status, time, evidence, and the version `reference`, `conclusion`, `hold` and `holdScope` when recorded); reconcile outcomes add a `conclusion`, and every `unverified` outcome from the tool records `holdScope`.
- **States.** `pending` (recorded before the write) → `executed` (read-back of the approved calendar and account matched every compared approved field, listed in the [procedure](google.md#approved-google-calendar-writes-root-procedure); other returned fields such as visibility, color or attachments are not compared; needs `verifiedAt`, `remoteRef` = queried `calendarId/eventId`, evidence) or `unverified` (any mismatch or unknown outcome). `unverified` → `executed` only after an exact read-back. Every `unverified` outcome of a claim (from its `pending` receipt until it ends) keeps `holdScope: {start, end, calendars, matches}`: the marked events the claim has seen, held or not. That is every marked event any reconcile saw, on the destination or another calendar and also in an incomplete or erroring search (the events it did see exist) or with times that cannot be read, plus a read-back event that carries the marker, each as `calendarId/eventId` with its calendar and interval, and the window and read calendars of every search that saw several at once. A search window counts only when both bounds are valid instants. The scope is the union over all of the claim's outcomes (the current receipt and its `attempts` since the pending one), so it never shrinks. An event's identity is its calendar and ID together: the same ID on another calendar is a second event, and the same event seen again is not. Once two or more distinct marked events have been seen, by one search or across several, the receipt also keeps `hold: "ambiguous"`. The hold survives later unknown, partial, unmarked, empty and other-calendar reconciles, and no direct read-back or `not_created` is accepted meanwhile. Only a complete reconcile that finds exactly one marked event, on the destination and none elsewhere, clears it, and only when its reads span from at least the earlier of `holdScope.start` and 24 hours before the action to the later of `holdScope.end` and 24 hours after it, and include every `holdScope` calendar. A narrower single match stays `unverified` and names what is still to be read. With exactly one marked event seen, a direct read-back may open only that event, and a reconcile that finds only it reads it back; any other event makes it a hold.
  - **Unknown range.** A hold with no `holdScope` (recorded before scopes were kept), an unreadable scope (bad times, calendars or matches that are not lists of IDs), several marked events seen by a search without valid bounds, or a marked event without a calendar or event ID or with times that cannot be read, sets `holdScope.unknown: true`. So does an earlier `unverified` outcome of the claim recorded without `holdScope` (before every outcome kept one), unless it shows no marked event was seen (an `unmarked` look-alike, or an empty search too narrow for absence). The flag stays set, later searches still add what they see, readable parts are kept and no range is invented. No search can be shown to cover an unknown range, so nothing clears it automatically: no read-back, reconcile or `not_created` is accepted, and the tool says it needs the human. Dayweave has no command to record that human resolution yet, so the action stays `unverified` and keeps blocking its time.
  - `not_created` needs a claim that has seen no marked event, and complete fresh reads of every queried calendar from at least 24 hours before to 24 hours after the action with no marked event; it states absence only for that window, never globally. Nothing retries automatically. A `not_created` action is never claimed again (`pending`) under a version it was not created under, even while another action of that version is still pending (the version reads `pending` until all settle, then `failed`), and even after a later version attempted it again: every `not_created` state in the receipt and its `attempts` refuses its `reference`. Earlier `not_created` states recorded before attempts kept a reference refuse every version prepared at or before them; one whose time cannot be read refuses every version (fails closed, no time is invented), so that action cannot be retried with the tool. The refusal applies only to new pending claims: a claim that already started records its read-back or reconcile outcome under its own version. A retry needs a newly prepared and approved version.
- Started actions keep blocking time and covering their work for the planner through their frozen approval copies ([daily plans](#daily-plan-recommendations)); receipts' `sourceRefs` and `minutes` are a fallback.
- Review shows each version's actions as prepared, pending, unverified, executed, not created or invalidated, with recorded times, remote event, key, approval text, evidence, earlier states (with their versions) and source IDs. Not created reads "Not created · absent in searched window": the evidence names that window, and nothing is claimed outside it. Pending, partial and unverified versions are listed under "In progress".
